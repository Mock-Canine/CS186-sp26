ConcatBacktrackingIterator

Flattens an iterator of BacktrackingIterables into a single backtracking stream. The interesting part is how it keeps mark / reset honest when the mark lives inside a chunk and later chunks are still lazy.

File: ConcatBacktrackingIterator.java Used by: Table.ridIterator() Source Q&A: concat-backtracking-iterator-qa.md
TL;DR Simulator Shape of the class Mental model Q&A Pitfalls

The one idea

Treat outerIterator as a one-way lazy source of chunks. Cache every chunk ever seen in iterables. Do all backtracking inside the inner iterator that holds the mark, then use indexes to resume forward through already-cached chunks.

Why you keep getting confused

There are two levels of position: which chunk (outer) and where inside that chunk (inner). Marks live at the inner level. The three index fields exist only to glue an inner iterator object back to its slot in the cached chunk list.

2Shape of the class

Six fields. Three iterator references, three indexes that say which chunk each reference came from.

private BacktrackingIterator<BacktrackingIterable<T>> outerIterator;  // lazy chunk supplier
private List<BacktrackingIterable<T>> iterables;                  // every chunk seen so far

private BacktrackingIterator<T> prevItemIterator;   // produced the last item
private BacktrackingIterator<T> nextItemIterator;   // will produce the next
private BacktrackingIterator<T> markItemIterator;   // holds the mark

private int prevIndex = -1;  // which slot in `iterables` these point to
private int nextIndex = -1;
private int markIndex = -1;

3Mental model

The single insight that makes the rest obvious.

A mark is not "at chunk N." It is at position P inside the inner iterator of chunk N. outerIterator.reset() can only rewind to chunk boundaries, so it is the wrong primitive. Instead, the inner iterator object itself remembers position P (via its own markPrev/markNext), and the concat iterator just holds a reference to that object.

Once you accept that, every field has an obvious job:

FieldQuestion it answersUsed in
nextItemIteratorWhere, inside a chunk, will the next value come from?hasNext, next
nextIndexWhich chunk slot does nextItemIterator live in?moveNextToNonEmpty
prevItemIteratorWhich inner iterator produced the last value? (needed so markPrev can ask that iterator to mark its own prev)markPrev
prevIndexWhich chunk slot did the last value come from? (becomes markIndex on markPrev)markPrev
markItemIteratorWhich inner iterator object holds the mark's exact inner position?reset
markIndexWhich chunk slot does markItemIterator live in? (so after reset, we can walk forward through later cached chunks)reset → moveNextToNonEmpty

4Q&A — the things I had to think twice about

Q1Why an EmptyBacktrackingIterator instead of null?›

Null-object pattern. The constructor sets nextItemIterator = new EmptyBacktrackingIterator<>() so the very first hasNext() can do this without a null guard:

if (!this.nextItemIterator.hasNext()) this.moveNextToNonEmpty();

It also gives markPrev/markNext/reset safe no-ops before any real iterator is in play.

Q2Why does markPrev() bail when prevIndex == -1?›

Two situations both leave prevIndex == -1: (a) no next() has ever been called, and (b) reset() was just called and we have not produced a new "previous" yet. In both cases there is nothing meaningful to mark. reset() explicitly nulls these out:

prevItemIterator = null;
prevIndex = -1;

So "after reset, markPrev is a no-op until you call next() again" — that is a deliberate contract.

Q3Why does markNext() call hasNext() first?›

So nextItemIterator is guaranteed to point at a non-empty chunk before we ask it to markNext(). Otherwise you'd happily call markNext on an exhausted (or empty) inner iterator and the mark would be meaningless.

Concretely, with chunks [1,2], [], [3,4] after next→1, next→2: nextItemIterator is still on chunk 0 (now exhausted). markNext() calls hasNext(), which runs moveNextToNonEmpty(), which skips chunk 1 and lands on chunk 2. The mark correctly ends up on 3.

Q4Could we delete iterables? It feels redundant with outerIterator.›

No. outerIterator only flows forward. Once moveNextToNonEmpty has pulled chunk 1 and chunk 2 to scan past them, those chunks are gone from the outer stream's "future." After a reset back into chunk 0, the concat iterator still needs to replay chunks 1 and 2 in order — and the only place they survive is iterables.

Compact version: outerIterator is forward-only from the concat iterator's perspective (it never calls outerIterator.reset()). The cache exists to make reset cheap and lossless without needing outer rewind.
Q5Why BacktrackingIterable rather than BacktrackingIterator in the type parameter?›

An Iterable is a factory for iterators; an Iterator is consumable, single-traversal state. The concat iterator wants to cache chunk identities, not consumed iterator objects. In practice this matters because:

this.nextItemIterator = iterables.get(nextIndex).iterator();  // fresh inner iterator over an old chunk

If the outer yielded Iterator directly, you'd have one already-mutated iterator per chunk and no way to create a fresh traversal. PageIterator ships BacktrackingIterable<RecordId> per page exactly so each page can be re-iterated.

Q6If we already have markIndex, why also keep markItemIterator?›

Because iterables.get(markIndex).iterator() gives a fresh iterator over the chunk — its internal cursor is at 0 and its internal mark is unset. The mark we care about lives inside the specific iterator instance we previously called markPrev() on. Throw that instance away and the mark is lost.

Tempting but broken
// Reconstruct from index alone
var iter = iterables.get(markIndex).iterator();
iter.reset();  // no-op; never marked
What the code actually does
// Keep the iterator instance that holds the mark
nextItemIterator = markItemIterator;
nextItemIterator.reset();   // restores inner position
nextIndex = markIndex;

Mnemonic: iterators remember inner position, indexes remember outer position. You need both.

Q7Could we just call outerIterator.markPrev() / reset() and skip all this bookkeeping?›

This is the question that took me longest. Two problems with that idea:

  1. Wrong granularity. Outer mark/reset operate on chunks. Our mark may be at value 2 inside chunk 0 — that is sub-chunk granularity. Outer rewind can only restore you to a chunk boundary.
  2. Wrong boundary. Even if you also held an inner mark, outerIterator.markPrev() would mark the current chunk (the marked chunk). After replaying the marked inner iterator to completion, you'd want to continue with the next chunk — so you'd need outerIterator.markNext() instead, plus extra state to remember "I am currently replaying the saved inner iterator and should not yet consult outerIterator."

Once you list all the bookkeeping that hybrid design would need (mark synchronization across outer + inner, what to do when no next chunk exists yet, what about empty chunks between mark and next, what if mark is updated multiple times…), it is strictly more complex than caching chunks in a list and using three integer indexes.

Q8Does outerIterator actually need to be a BacktrackingIterator?›

No — only hasNext() and next() are ever called on it. A plain Iterator would suffice. The stronger type is there because callers (PageIterator, etc.) already return BacktrackingIterator, and asking for the more specific type avoids an awkward upcast at the call site.

5Pitfalls to re-check before exam

Wrong intuition

"Reset means rewind outerIterator."

Right intuition

Reset means restore one inner iterator (markItemIterator) to its inner mark, then let moveNextToNonEmpty walk forward through the already-cached chunks via nextIndex.

Wrong intuition

"prevIndex exists for moveNextToNonEmpty."

Right intuition

prevIndex is only used by markPrev — to copy prevIndex → markIndex together with prevItemIterator → markItemIterator. Resetting nulls it out (= -1) because there is no longer a meaningful "previous."

Wrong intuition

"markNext() remembers the next value as it stands now."

Right intuition

It first advances nextItemIterator past any empty / exhausted chunks (via hasNext) and only then marks. So with chunks [1,2], [], [3] after consuming 1 and 2, markNext marks 3, not "the end of chunk 0."

Subtle: after reset() followed by enough next() calls to exhaust the marked chunk, moveNextToNonEmpty does iterables.get(nextIndex+1).iterator(). That creates a brand new inner iterator for the next chunk, throwing away whatever cursor state that chunk's earlier iterator instance had. That is fine because the mark only ever lived in one chunk, and after a reset there are no live references to those discarded iterators.
