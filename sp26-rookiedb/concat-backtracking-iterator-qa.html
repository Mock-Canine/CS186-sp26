CS186 RookieDB review

Flatten chunks, but remember where reset must land.

The main idea is two-level position tracking. Inner iterators remember item-level state. Indexes remember which cached chunk those iterator objects belong to.

Original markdown Q&A Class: ConcatBacktrackingIterator.java Pattern: one self-contained HTML note

Core Takeaways

  • It flattens an iterator of chunks. The caller sees one stream even though the data arrives as many `BacktrackingIterable` objects.
  • `iterables` is a replay cache. Once the outer iterator yields a chunk, the concat iterator saves the reusable chunk so reset can move backward and then continue forward.
  • Iterator references hold inner state. `prevItemIterator`, `nextItemIterator`, and `markItemIterator` know positions inside one chunk.
  • Indexes hold outer state. `prevIndex`, `nextIndex`, and `markIndex` say which cached chunk each iterator reference came from.

One Sentence

`ConcatBacktrackingIterator` is not just concatenating; it is concatenating while preserving a mark that may live inside one chunk and still allowing forward replay through later chunks. 

outer level: which chunk?
inner level: which item inside that chunk?

Field Map

nextItemIterator + nextIndex

Where the next call to `next()` will read. `nextIndex` is required so `moveNextToNonEmpty()` can jump to the following cached chunk.

prevItemIterator + prevIndex

Where the last returned item came from. `markPrev()` copies these into the mark fields.

markItemIterator + markIndex

Where reset must return. The iterator reference stores item-level mark state; the index stores chunk-level position.

iterables

A cache of chunks already discovered from the outer iterator. This is what lets replay continue after resetting backward.

outerIterator

A lazy chunk supplier. This class only uses `hasNext()` and `next()` on it, even though it is typed as a `BacktrackingIterator`.

EmptyBacktrackingIterator

A null-object starting value, so `nextItemIterator.hasNext()` is safe before the first real chunk is loaded.

Confusions Worth Remembering

Why keep `iterables`?

Because the outer iterator is forward-moving. If reset returns into chunk `0`, the concat iterator still needs a way to replay chunk `1`, chunk `2`, and so on. The cached `BacktrackingIterable` objects are reusable chunk sources. 

next() -> 1
next() -> 2
markPrev()
next() -> 3
next() -> 4
reset()
next() -> 2
then still continue with 3, 4, ...
Why not just use `outerIterator.reset()`?

The outer iterator knows chunk boundaries, not positions inside a chunk. A flattened reset may need to return to value `2` inside chunk `[1,2,3]`, then continue to the next chunk. That requires inner iterator state plus chunk-level bookkeeping.

Why keep both iterator references and indexes?

A fresh `iterables.get(index).iterator()` starts at the beginning of a chunk. It does not know where the old iterator had advanced or marked. The iterator reference preserves inner state; the index tells the concat iterator where that state belongs in the cached chunk list.

Why use `BacktrackingIterable` rather than `BacktrackingIterator` as the chunk type?

An iterable is a reusable chunk. The concat iterator can cache the chunk and create a fresh iterator when it moves to that chunk again. A bare iterator is already a mutable traversal state.
